# CITS-to-go Android App

Android app for the **CITS-to-go** portable C-ITS receiver.

The app reads and writes the bidirectional `CTG1` USB protocol, records
received packets to PCAP, forwards captures to MQTT, sends arbitrary raw
802.11 frames, and generates ETSI CAM messages.

> **AI generation notice:** this Android app is part of a repository that is approximately **95% generated by AI**. Review, test, and audit the code before relying on it for field use.

## Downloading the app

The latest debug APK can be downloaded from the releases page:

<https://codeberg.org/sascha8a/cits-to-go/releases>

The app's **Flashing** navigation item looks up the Codeberg release whose tag
matches the installed app version, verifies the merged ESP32-C5 firmware
artifact against `SHA256sum.txt`, and flashes a connected XIAO ESP32-C5 over
USB. A running receiver (USB or Bluetooth) is stopped automatically when you
pull the flash slider; connect the board directly to the Android USB
host, and put the ESP32-C5 into boot mode: hold **BOOT** while connecting or
resetting the board, and keep it held until flashing starts. Then pull the
confirmation slider fully to the right. After flashing, restart the receiver
from the Home page.

## Running the app

### Connection diagnostics

Logging starts automatically when the app process starts. To report a USB or
Bluetooth problem, reproduce it, open **Logs** in the navigation drawer, and tap
**Export all**. Attach the saved text file to the bug report along with what you
were doing. Export includes all retained levels, regardless of the screen filter.

The screen shows timestamps (UTC), source, and Debug/Info/Warning/Error severity,
with minimum-level filters and a Clear action. History is limited to the latest
2,000 entries in memory; it is lost when Android terminates the process. Individual
messages and stack traces are truncated to 8,192 characters each. Export before
restarting the app. Exports include app/Android/device versions and connection
details; packet payloads are not logged.

Connection diagnostics include USB inventory and selection decisions, permission
prompt/callback state, per-transport attempt IDs, BLE setup stages and elapsed
connection time, and the first bytes, valid CTG frame, and firmware statistics.
Normal capture has no separate request/response handshake: the first valid CTG
frame confirms protocol communication. USB enrollment additionally logs the
firmware acknowledgement and encrypted BLE verification. Repeated empty reads,
notifications, and malformed records are limited to preserve startup context.

Diagnostics use `java.util.logging.Logger`. A root `Handler` collects propagated
JUL records while preserving existing handlers. App loggers under
`org.opentrafficmap.citstogo` enable debug (`FINE`) records; other loggers retain
their own thresholds. `SEVERE` maps to Error, `WARNING` to Warning, `INFO` to Info,
and lower levels to Debug. This does not capture arbitrary `android.util.Log`
calls or system Bluetooth stack logs.

### Capture

1. Flash the CITS-to-go firmware to the XIAO ESP32-C5.
2. Connect the XIAO to the Android phone with a USB-C data cable.
3. Open the app.
4. Grant USB permission.
5. Configure the MQTT broker URI and node ID.
6. Start capture.
7. Use **Record PCAP** to choose an output file if local capture is needed.
8. Confirm packet, PCAP, and MQTT counters increase.

To transmit a raw frame, paste its hexadecimal bytes into **Raw 802.11
transmit** and tap **Transmit packet**. The frame must include its 802.11 MAC
header and must not include an FCS.

To broadcast CAM:

1. Unlock transmitting first: shake the phone firmly until the **TX Approval**
   screen opens, tick the confirmation, then pull the red handle fully from left
   to right. Until then, the **CAM Broadcast** page is hidden and CAM and SREM
   transmissions are blocked. The approval is stored and can be revoked in
   **Settings** with **Revoke TX Approval**. Transmitting in the 5.9 GHz ITS band
   is regulated, see [RF safety](../docs/CAM.md#rf-safety).
2. Choose the vehicle profile on the **CAM Broadcast** page or under
   **Settings → Vehicle Type**; SREM requests use it as well. On the CAM
   Broadcast page a change applies at once, also during a broadcast, and Home
   shows the active profile.
3. Start a capture on **Home**. Then set a 100–1000 ms maximum interval on the
   **CAM Broadcast** page, tap **Start CAM broadcast** and grant location
   permission.
4. Watch the TX and CAM acknowledgement counters.

The configured interval is the maximum interval. The generator also applies
the ETSI dynamics triggers (over 4 m position change, 4° heading change, or
0.5 m/s speed change) while respecting the 100 ms minimum interval. Broadcast
waits until the phone has a fresh location, because GeoNetworking source
position vectors cannot carry CAM latitude/longitude “unavailable” values.

CAMs are Release 1 UPER messages (`protocolVersion=2`, `messageID=2`) carried
over BTP-B destination port 2001, GeoNetworking SHB, EtherType `0x8947`, and a
broadcast QoS 802.11 data frame. See [CAM implementation notes](../docs/CAM.md).

The bridge runs as a foreground service with a partial wakelock while capture is active, so USB capture and MQTT forwarding continue while the phone is locked. MQTT publishes are retried through an app-private disk spool when the broker is offline.

PCAP output is classic libpcap with `DLT_IEEE802_11` link type and raw 802.11 frame bytes. It includes received packets and packets acknowledged as successfully transmitted by the firmware.

### Map

The **Map** page shows received CAM stations and DENM events on an OpenFreeMap base map, with the phone's own
position. It works during a capture or a PCAP replay and needs a data connection for the base map. Markers turn grey
after 3 s without a CAM and disappear after **Settings → Map → Station timeout** (default 10 s). Tap a marker for its
details. The history button adds the road side units and traffic lights heard before, optionally limited under
**Settings → Map → Road side units heard within**. See [map view notes](../docs/MAP_VIEW.md).

### Battery settings for long captures

Android's battery optimisation can still stop or throttle the app a few
minutes after the screen turns off, even with the foreground service and
wakelock. A capture then ends early. Before long captures, exempt
**C-ITS to go** from battery optimisation. Menu names differ between Android
versions and manufacturers; if you can't find an entry, search the Settings app
for "battery".

- **Android 12 and newer:** Settings → Apps → C-ITS to go → Battery (or
  "App battery usage") → **Unrestricted**.
- **Android 8 to 11:** Settings → Apps → Special app access → Battery
  optimisation → All apps → C-ITS to go → **Don't optimise**.

Many manufacturers add their own background limits on top of Android's:

- **Samsung:** Settings → Battery → Background usage limits. Make sure the app
  is not listed under "Sleeping apps" or "Deep sleeping apps", and add it to
  "Never sleeping apps".
- **Xiaomi, Redmi, POCO:** App info → Battery saver → **No restrictions**, and
  turn on **Autostart**.
- **Huawei, Honor:** Settings → Battery → App launch → C-ITS to go → turn off
  "Manage automatically" and allow all options.
- **OnePlus, Oppo, Realme:** App info → Battery usage → allow background
  activity.

System-wide power saving modes can also limit background work, so leave them
off while capturing. For other devices see <https://dontkillmyapp.com>.

To check the setting, lock the phone for at least 10 minutes during a capture
and confirm that the packet, PCAP and MQTT counters kept increasing.

## MQTT output

The packet stream matches the upstream OpenTrafficMap receiver firmware.
Captured packets and packets acknowledged as successfully transmitted by the
firmware are published to the same topic:

```text
Topic:   its/<nodeid>/packet
Payload: raw binary packet bytes
QoS:     0
Retain:  false
```

The app also publishes retained `its/<nodeid>/status` messages (`online`/`offline`), `its/<nodeid>/info`, and periodic `its/<nodeid>/stats`.

```text

```

Install it with the below command, or send it to the phone and install with a file explorer:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

## Gesture regression tests

Swipes on ordinary page content open the navigation drawer. Horizontal gestures
inside a slider (including a disabled slider or the track away from the thumb)
belong to that control, not the drawer. Only enabled thumb drags change the value;
vertical gestures on sliders remain available for page scrolling. The map owns
its pan/zoom gestures, and pagers, horizontally scrolling tables and resize handles
consume their own drags, including at scroll boundaries.

With an unlocked Android device or emulator connected, run from `android-app/`:

```bash
nix-shell shell.nix --run './gradlew connectedDebugAndroidTest'
```

The regression suite uses the real Material navigation drawer and includes the
intersection renderer. Check Android 12/MIUI as well as newer Android releases.

## Bluetooth enrollment

Bluetooth is not open-pairing. Connect CITS-to-go over USB, select the USB device, and tap **Enroll this phone for Bluetooth**. The app sends a USB-only enrollment command and asks Android to create the BLE bond. Firmware permits exactly one new pairing attempt for 30 seconds and replaces the previous owner bond.

After enrollment, select **Bluetooth** and start normally. Android and NimBLE authenticate using the stored BLE bond and encrypt the link; the CTG application protocol does not perform a separate login or challenge-response. Unknown/unbonded phones are ignored by the app and rejected by firmware.

## Debug diagnostics

Enable **Settings → Debug menu** to add a Debug destination to the navigation drawer. It shows Android CTG stream-gap/protocol counters, Android BLE MTU/PHY state, and the firmware's 1 Hz CTG1 statistics record including Wi-Fi RX/capture/output rates, queue occupancy, drop counters, BLE notifications, connection interval/latency/supervision timeout and PHY. See `../docs/DEBUG_DIAGNOSTICS.md` for interpretation.

## Intersection packet parsing

MAPEM/SPATEM extraction supports both unsecured and secured GeoNetworking. Secured packets are parsed without assuming a fixed security-header size, and the GeoNetworking payload length bounds the ITS PDU so security trailers are excluded before UPER decoding. MAPEM regional open types that are not needed for standard lane geometry are safely skipped. Enable the Debug menu to inspect intersection extraction/decoding counters and the latest decoder error. See `../docs/INTERSECTION_DECODING.md`.
